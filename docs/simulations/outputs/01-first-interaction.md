# First Interaction — Glider meets Block

> The riskiest assumption test: does a glider traveling across a medium grid meaningfully reach and interact with a block, and does the result produce a legible ownership outcome that a human player could reason about?

## Setup

- **Grid:** 12 × 12
- **Palette:** Block, GliderSE, BlinkerH
- **Advance steps per turn:** 4
- **Rules:** Standard Conway + majority-of-parents ownership, advanceSteps=4 so each turn moves a glider by exactly 1 diagonal cell

### Design questions this scenario tests

- Does a glider meaningfully travel across a 12x12 in a reasonable number of turns?
- When a glider hits a block, is the outcome visually legible?
- Does the ownership propagation feel natural (debris colored by parent majority)?
- Does this scenario feel like a game where decisions matter?

## Strategic analysis

### Summary

Final score **P1: 0, P2: 8**. A total rout. P1 never held territory past turn 2.

This scenario ran clean — the simulator executed every Conway step correctly, ownership tracked correctly, rendering is readable. And it exposed three findings that would have taken **hours** to discover by building a real prototype.

### What worked — mechanical validation

1. **Gliders travel at exactly the expected pace.** With `advanceSteps=4`, each turn the glider shifted exactly +1 row, +1 col. A glider from (0,0) reached column 6 in about 6 turns. That feels right — fast enough to create pressure, slow enough to plan defense. **Decision: `advanceSteps=4` is the right default.** Lock this in.
2. **Placement collision handling works correctly.** When P2's second glider at (2,0) tried to overlap P1's first glider's wake, the overlap cells were skipped (default `allowOverwrite: false`). No silent corruption.
3. **Rendering is readable** with row+column numbers. You can follow patterns by eye and point to specific cells in discussion. The `.`/`X`/`Y`/`*` legend works.
4. **The script cost 0 credits** to run the entire 8-turn, 32-Conway-step simulation. This is the correct architecture.

### What broke — design findings (the important part)

#### 🚨 Finding 1: Adjacent blocks destroy each other

This is the single most important finding from this scenario. **P1's defensive strategy — placing a second block adjacent to the first — collapsed both blocks in one Advance.**

Look at T2 place:
```
 6 ......XX....
 7 ......XXX...
 8 .......XX...
```

A naive player sees two blocks forming a wall. But in Conway's rules, this is a 7-cell shape, not two stable blocks. The (7,7) cell is now shared between both "blocks," and the resulting neighbor counts make most cells overcrowded. After 4 Conway steps, all 7 cells are gone.

**Implications for the real game:**
- A beginner's first instinct will be to "build walls" by placing blocks next to each other. That instinct is punished instantly. They lose their entire territory on one turn and won't understand why.
- **The game MUST prevent this footgun** or the onboarding experience is catastrophic. Three options:
  - **Option A — Preview:** show a ghost of the post-Advance state as the player positions a pattern. They'd see their blocks dissolving before placing.
  - **Option B — Placement buffer:** enforce a 1-cell empty buffer around each placed pattern. Prevents adjacency but limits strategic density.
  - **Option C — Rule enforcement:** detect unstable combinations at placement time and visually warn. Harder to implement but preserves freedom.
  - **My recommendation:** Option A (ghost preview). It teaches through experience rather than constraint, and it's the same mechanism we'd want anyway for strategic play.

#### 🚨 Finding 2: Placing patterns in the wake of a traveling spaceship corrupts them

Look at T3's place vs what P2 intended. P2 tried to deploy a clean glider at (2,0). But the existing first glider had moved to that area, and the overlap rule skipped cells:
```
 4 YYYYY.......
```

What P2 got wasn't a glider — it was a merged 5-cell shape that then evolved chaotically into whatever the sim shows in T4-T5.

**Implications:**
- Players can't reliably predict where their patterns land if the board already has movement. A glider defender might find their defensive block placed into a wake of corruption.
- This is probably **fine** as a strategic element — "you have to think about where patterns WILL be, not just where they ARE now" is good chess-like depth — but it only works if there's **preview**. Without preview it's random punishment.

#### 🚨 Finding 3: The ownership propagation never got tested

No mixed-parent births occurred because the two players' patterns never had 3-cell adjacency across the color boundary. **We don't actually know if the majority-of-parents rule produces legible results.** Need another scenario specifically designed to force mixed births.

Proposed next scenario: place a P1 block and a P2 blinker immediately adjacent so that next Advance creates contested birth cells. Observe what color they end up, and whether the coloring tells a clear story.

### What this means for the pivot direction

The pivot to pattern-based play is **mechanically workable** — patterns travel, collisions work, ownership tracking works. But it's **pedagogically brutal** without preview. A beginner placing "two blocks next to each other" thinking they're building a wall will lose the game before understanding what happened.

**The game cannot ship without a ghost preview of the post-Advance state.** I called this out in the earlier "meaningful play" diagnosis, and this scenario confirms it empirically. Preview is not optional — it's the core bridge between Conway's chaotic physics and human intuition.

### Feel notes (estimated, single scenario)

This simulation doesn't include a human player, so "feel" is extrapolated. But some observations:

- **Decision time per move:** probably 20-40s for intermediate players, because they need to think about *where* patterns will be after advance, not just where they are now. Higher than chess-move time (10-20s). This could be okay, could be too slow. Depends on match length.
- **Match length:** this scenario was 8 turns of actual placement + advances. Taking 30s per turn × 8 turns = 4 minutes. That's a reasonable chess blitz length. Longer games with more patterns might run 8-15 minutes.
- **Tension curve:** flat in this scenario because P1 lost on turn 2 and then just watched P2 dominate. A real game would need a way for losing players to come back, or matches would feel hopeless once someone makes one mistake.

### Decision time per move (estimated)

- **T1 P2 Glider:** 10s. Opening move, easy to reason about.
- **T1 P1 Block:** 15s. Trying to anticipate the glider's path.
- **T2 P1 Second Block:** 20s. Wanted to reinforce. (Would have been 2+ minutes if the player had the information to know adjacent blocks fail — they'd search for a better option.)
- **T3 P2 Second Glider:** 30s. Choosing an angle that doesn't collide with the first glider's wake.
- **T4-T8 Advance-only turns:** 5s each (no placement decision).

### Verdict

**Mechanical correctness: ✅ PASS.** The script's Conway step, placement, ownership propagation, and rendering all work correctly.

**Design viability: ⚠️ CONDITIONAL.** The pivot direction is workable **only if we add ghost preview**. Without preview, beginners will lose games for reasons they can't perceive. With preview, they can learn cause and effect.

**Next scenarios to run:**
1. **Mixed-parent birth test** — force contested births, see if ownership coloring is legible.
2. **Pattern-pair safety matrix** — test which pairs of patterns are safe to place adjacent. This will become a cheat sheet for the onboarding.
3. **Preview effectiveness test** — simulate a player who has preview information (we annotate optimal moves) vs. a player who doesn't, and see how different their games look.
4. **Grid size test** — run the same scenario on 8x8, 12x12, 16x16, 20x20. See which grid size supports the most legible pattern interactions.

### One big surprise from this run

Before running the scenario, my intuition was that "glider hits block" would be the interesting moment — the climactic collision. Instead, **the interesting moment was P1's own second block destroying the first one**. The glider never even reached the target. P1 killed themselves by misunderstanding Conway's adjacency rules.

This tells me the hardest design problem isn't "make patterns interact interestingly" (Conway does that for free). The hardest problem is **"make the player understand what their own move will do"**. Ghost preview solves both.
